    Marianne CLI Reference¶

    Complete reference for all Marianne CLI commands and options. Marianne provides a single entry point:

    • mzt — Score orchestration CLI (run, monitor, diagnose, learn, conductor management)

    Global Options¶

    These options apply to all mzt commands:

    Option Short Description Env Var
    --version -V Show version and exit
    --verbose -v Show detailed output with additional information
    --quiet -q Show minimal output (errors only)
    --conductor-clone Route all daemon interactions to a clone conductor (see below)
    --log-level -L Logging level: DEBUG, INFO, WARNING, ERROR MZT_LOG_LEVEL
    --log-file Path for log file output MZT_LOG_FILE
    --log-format Log format: json, console, or both MZT_LOG_FORMAT
    --help Show help message

    Conductor Clones¶

    The --conductor-clone option starts or connects to a clone conductor — an isolated conductor instance with its own socket, PID file, state database, and log. This lets you test scores, CLI features, and conductor behavior without risking your production conductor.

    # Start a default clone conductor
mzt --conductor-clone start

# Submit a score to the clone
mzt --conductor-clone run my-score.yaml

# Check clone status
mzt --conductor-clone status

# Named clones for parallel testing
mzt --conductor-clone=staging start
mzt --conductor-clone=staging run staging-test.yaml
mzt --conductor-clone=staging conductor-status

# Stop the clone when done
mzt --conductor-clone stop

    Key behaviors: - The clone inherits your production ~/.marianne/conductor.yaml config unless overridden. - Clone paths: ~/.config/mzt/clone.sock (socket), ~/.config/mzt/clone.pid (PID file). - Named clones use the name in the path: ~/.config/mzt/clone-staging.sock. - Clone names are sanitized (64 character limit, safe characters only). - Commands that don't interact with the conductor (validate, --help) ignore this flag.

    Core Commands¶

    mzt run¶

    Run a score from a YAML configuration file.

    Usage: mzt run [OPTIONS] CONFIG_FILE

    Arguments¶

    Argument Required Description
    CONFIG_FILE Yes Path to YAML score configuration file

    Options¶

    Option Short Default Description
    --dry-run -n false Show what would be executed without running. The preview renders with any --var overrides merged, exactly as the conductor would run the score
    --start-sheet -s Override starting sheet number
    --json -j false Output result as JSON for machine parsing
    --escalation -e false Pause sheets in FERMATA on retry exhaustion for a composer decision; resolve with mzt resolve. Works without --self-healing
    --self-healing -H false Enable automatic diagnosis and remediation when retries are exhausted
    --yes -y false Auto-confirm suggested fixes when using --self-healing
    --require-lock (none) Admission gate (GH #403): path to the composition lock the composing skill's release gate wrote (check_score_release.py --write-lock). The conductor verifies the lock's score_sha256 against the exact bytes it is about to parse; a missing, stale, unreadable or malformed lock rejects the job with that reason. Omit for ordinary unlocked submission.
    --fresh false Re-run a score from scratch: re-register all sheets and, when the score sets workspace_lifecycle.archive_on_fresh, archive non-preserved workspace files first. Auto-triggered for completed scores when the YAML changed. skip_when unchanged rules are evaluated on fresh runs; to force a sheet to re-run, use mzt resume --force --from-sheet 1, remove the rule, or delete <workspace>/.marianne/pass-ledger/.
    --job-id (score filename) Name this run (GH #505). The job ID defaults to the score file's stem; --job-id NAME lets one shipped score serve several commissions side by side without a renamed copy. When the score omits workspace:, the auto-managed workspace follows the name too (~/workspaces/NAME); an explicit workspace: still wins. Use the same name with status, pause, resume, resolve and cancel. Must start with a letter or digit; after that letters, digits, ., _ and -, at most 100 characters. An invalid --job-id is a usage error (exit 2, reported on stderr) and nothing is submitted; with --json stdout stays empty for it. Not supported for fleet configs. A type: fleet member is named <fleet>--<stem> by the fleet itself (GH #514), so two fleets with an integration.yaml never share a job ID.
    --var (none) Per-invocation template variable as key=value (repeatable). Merges into the score's prompt.variables, CLI overriding YAML on collision — point one generic score at different inputs without editing it. Values are strings (typed vars belong in YAML). Persisted across resume and inherited by every job a concert trigger chains from this one.

    Auto-Fresh Detection¶

    When you re-run a completed score after editing the YAML file, Marianne automatically detects the change and starts fresh — no --fresh flag needed. The conductor compares the score file's modification time against the previous run's completion time. If the score is newer, it starts a fresh run automatically.

    This only applies to completed scores. Failed or paused scores are always resumed from their checkpoint, regardless of file changes.

    Backpressure and Rate Limits¶

    The conductor rejects new score submissions only when the system is under resource pressure (high memory usage or too many child processes). Rate limits do not cause job rejection — they are per-instrument concerns handled at the sheet dispatch level by the baton. A rate limit on one instrument does not block scores targeting different instruments.

    If the system is under resource pressure, mzt run exits with an error:

    Error: System under high pressure — try again later.

    Recurring-score lifecycle¶

    For a score with schedule:, mzt run score.yaml is both trigger-now and schedule registration/replacement. Use the existing lifecycle commands against the stable schedule/score ID: mzt status and mzt list show next/last due and outcome; mzt pause ID stops future ticks (and active lineage), mzt resume ID re-arms one durable next due, and mzt cancel ID removes the schedule. After a conductor restart, the registry restores one future timer or one latest catch-up; it never replays every missed interval.

    Examples¶

    # Basic run (requires running conductor: mzt start)
mzt run job.yaml

# Dry run to preview (works without conductor)
mzt run job.yaml --dry-run

# Start from sheet 3
mzt run job.yaml --start-sheet 3

# With self-healing enabled
mzt run job.yaml --self-healing --yes

# Fresh start (ignores existing state)
mzt run job.yaml --fresh

    Exit Codes¶

    Code Meaning
    0 Success or graceful shutdown
    1 Configuration error or score failure
    2 Usage error: an invalid option value such as --job-id 'has spaces', or a CONFIG_FILE that does not exist. Reported on stderr with nothing on stdout, --json included

    A score that does not load (malformed YAML, or one that fails the score schema) is checked before the conductor is contacted: exit 1, with {"error": "..."} on --json or the error and a Validate with: mzt validate FILE hint otherwise. agents run checks the score before probing the conductor too (GH #561): an invalid score is SUBMIT_REFUSED with invalid score FILE: and the score's own error as the hint, cut to 300 characters, so with the conductor down it reports the score rather than the conductor.

    mzt resume¶

    Resume a paused or failed score.

    Usage: mzt resume [OPTIONS] JOB_ID

    Loads the score state and continues execution from where it left off. By default, Marianne auto-reloads the config from the original YAML file if it still exists on disk. Falls back to the cached config_snapshot when the file is gone. Use --no-reload to force using the cached snapshot: the score exactly as it was admitted (or as the last reloading resume ran it), so edits made to the YAML on disk since then are ignored. The snapshot is written at submit and refreshed on every reloading resume.

    Resuming a failed or cancelled score (or passing --from-sheet) also reopens loops that ended in failure (range_failed, condition_error) when the reset left member sheets pending: the loop returns to running with its in-flight iteration preserved, so templates and validations see the loop index (e.g. {{ pass_no }}) again instead of failing with E999 on an undefined variable. A loop that ended for a genuine reason — condition_met, count_reached, max_iterations, cost_limit_exceeded — stays closed, with one exception: a loop that ended at max_iterations is reopened by --from-sheet when the score it reloads (the file on disk, or --config) sets a higher max_iterations for that loop. The next pass is numbered after the spent ones, so a composer who reads a capped result can grant more passes on the same work by raising the cap and resuming from the loop's first sheet (GH #584). Resuming a paused score preserves loop state as persisted. Each reopened loop is logged (baton.resume.loops_reopened) with the count and any from_sheet bound.

    Arguments¶

    Argument Required Description
    JOB_ID Yes Score ID to resume. A fleet's name resumes the fleet: every paused member, then any dependent group the fleet dropped when a dependency member failed, once that member (resubmitted under its <fleet>--<stem> ID) is complete (GH #515).

    Options¶

    Option Short Default Description
    --config -c Path to config file (optional if config_snapshot exists in state)
    --force -f false Force resume even if score appears completed
    --escalation -e false Pause sheets in FERMATA on retry exhaustion for a composer decision; resolve with mzt resolve. Works without --self-healing
    --no-reload false Use cached config snapshot instead of auto-reloading from YAML file
    --from-sheet Reset every sheet >= N to pending and re-run from there, including completed or skipped sheets; loops whose span still has a pending member sheet >= N are reopened with their iteration preserved
    --self-healing -H false Enable automatic diagnosis and remediation when retries are exhausted
    --yes -y false Auto-confirm suggested fixes when using --self-healing

    Examples¶

    # Resume paused score
mzt resume my-job

# Resume with explicit config
mzt resume my-job --config job.yaml

# Resume with explicit config file (overrides auto-reload)
mzt resume my-job --config updated.yaml

# Resume using cached snapshot (skip auto-reload)
mzt resume my-job --no-reload

# Force resume a completed score
mzt resume my-job --force

# Re-run from sheet 5 onward
mzt resume my-job --from-sheet 5

    Resumable States¶

    Status Resumable Notes
    paused Yes Continues from last sheet
    failed Yes Retries from failed sheet
    running Yes Continues from last sheet
    completed With --force Re-runs the completed score
    pending No Use run instead

    mzt pause¶

    Pause a running Marianne score gracefully.

    Usage: mzt pause [OPTIONS] JOB_ID

    Creates a pause signal that the score detects at the next sheet boundary. The score saves its state and can be resumed with mzt resume.

    Arguments¶

    Argument Required Description
    JOB_ID Yes Score ID to pause

    Options¶

    Option Short Default Description
    --wait false Wait for the score to acknowledge the pause signal
    --timeout -t 60 Timeout in seconds when using --wait
    --json -j false Output result as JSON
    --force -f false Force-cancel the score immediately without waiting for a sheet boundary

    Examples¶

    # Pause a running score
mzt pause my-job

# Pause and wait for acknowledgment
mzt pause my-job --wait --timeout 30

# Cancel immediately without waiting for a sheet boundary
mzt pause my-job --force

    mzt resolve¶

    Resolve a sheet paused in FERMATA awaiting a composer decision (#361).

    Usage: mzt resolve [OPTIONS] JOB_ID SHEET_NUM DECISION

    When escalation is enabled (--escalation or --self-healing), a sheet that exhausts its retries pauses in FERMATA instead of failing. mzt status lists pending decisions; this command records yours and the score continues immediately. (Equivalent to creating a marker file markers/fermata/<job_id>/sheet-<N>.<decision> under the job workspace.)

    Arguments¶

    Argument Required Description
    JOB_ID Yes Score ID with a sheet paused in FERMATA
    SHEET_NUM Yes Sheet number awaiting the decision
    DECISION Yes retry (re-run from scratch), skip (skip, continue dependents), accept (accept the last attempt as success), fail (fail it, propagate to dependents)

    Options¶

    Option Short Default Description
    --json -j false Output result as JSON

    Examples¶

    # Re-run a FERMATA'd sheet from scratch
mzt resolve my-score 3 retry

# Accept the sheet's last attempt as success
mzt resolve my-score 3 accept

    mzt modify¶

    Modify a score's configuration and optionally resume execution.

    Usage: mzt modify [OPTIONS] JOB_ID

    Convenience command that combines pause + config validation. If the score is running, it will be paused first. Use --resume to immediately resume with the new configuration.

    Arguments¶

    Argument Required Description
    JOB_ID Yes Score ID to modify

    Options¶

    Option Short Default Description
    --config -c required New configuration file

    JSON output (--json)¶

    --json is a machine contract on every command that offers it: stdout carries only the JSON document — valid UTF-8, ASCII-escaped, emitted verbatim (no emoji or markup substitution) — so a consumer can json.load(sys.stdin) it without an errors= policy (issue #495). Hostile bytes captured from musicians or subprocesses (a stray 0x97 em dash in an output tail, lone surrogates from a mis-decoded stream) are neutralized at the capture boundary before they reach state, and the JSON writer serializes with ensure_ascii=True through a direct stdout write that bypasses Rich's rendering pipeline. JSON-format logging (--log-format json) is pinned to the same ASCII-only serialization.

    Global JSON guarantees¶

    All --json output shares these guarantees (issue #495):

    • Strict UTF-8. mzt status <job> --json | python3 -c 'import sys, json; json.load(sys.stdin)' never raises UnicodeDecodeError, whatever a musician's subprocess printed.
    • ASCII-only serialization. Output is written with ensure_ascii=True; non-ASCII characters in values appear as \uXXXX escapes.
    • Verbatim emission. The serialized text is written directly to stdout (bypassing Rich's emoji substitution), so the payload a consumer parses is the payload json.dumps produced.

    Prompt receipt per sheet (GH #546)¶

    mzt status <job> --json gives every sheet that has assembled a prompt a prompt_receipt summary: total_bytes, estimated_tokens (a character-heuristic estimate, not a tokenizer count), source_count, dropped_count and prompt_sha256. The full receipt is the sheet's prompt_receipt in the checkpoint: ordered sources (kind prelude/cadenza/technique/memory/template, path as declared, resolved_path, sha256, bytes, truncated, dropped_reason), template_bytes, total_bytes, estimated_tokens and prompt_sha256. It holds hashes and sizes, never prompt text. An optional item over its max_bytes, or one that is missing or unreadable, appears with its dropped_reason and 0 bytes. Each attempt_history entry carries that attempt's model_used, prompt_sha256 and prompt_bytes. mzt diagnose lists each sheet's three heaviest sources and every dropped one.

    The guarantees are enforced by regression tests (tests/test_json_utf8_contract.py) that plant hostile bytes (raw 0x97, lone surrogates) in attempt output and assert the emitted JSON parses strictly.

    mzt watch¶

    Live-tail musician output for a running score (#352).

    Usage: mzt watch [OPTIONS] JOB_ID [SHEET_NUM]

    Streams each LLM's output as it generates, credential-redacted, over the conductor's job.output.stream IPC. The stream starts with the recent lines retained in the sheet's ring buffer (~256 KB per sheet, drop-oldest with an explicit [dropped N lines] marker), then follows new output until Ctrl-C.     Argument Required Description
    JOB_ID Yes Score ID to tail (see mzt status)
    SHEET_NUM No Sheet number to tail. Omit to tail ALL sheets — lines arrive tagged [s<sheet>]

    Examples¶

    # Tail every sheet of a running score
mzt watch my-score

# Tail only sheet 3
mzt watch my-score 3

    mzt wait¶

    Block until a score is finished or needs a human decision (GH #547).

    Usage: mzt wait [OPTIONS] JOB_ID

    The conductor has no per-score subscription, so the command polls it inside the process (2 s, backing off to 10 s). Rate-limit waits, retries and fallbacks happen inside the conductor and do not end the wait. Three polls in a row that cannot reach the conductor end it as conductor_down.

    Options¶

    Option Short Default Description
    --max -m 1800 Seconds to wait before reporting wait_expired
    --json -j false One JSON object, no ANSI

    Result¶

    {"state": "needs_you", "job_id": "my-job", "status": "paused", "outcome": "paused",
 "reason": "sheet 20 is at a fermata awaiting a decision: ...", "verdict": null}
    state Exit Meaning outcome
    done 0 The score finished completed or cancelled
    needs_you 2 A person must decide: the score failed, is paused, or has a sheet at a fermata (mzt resolve) failed or paused
    conductor_down 3 The conductor could not be reached null
    wait_expired 4 --max ran out while the score was still moving null

    An unknown score is the usual error envelope ({"success": false, "message", "hints"}) with exit 1. verdict is always null here; read it with mzt verdict.

    List what needs attention across scores, most urgent first (GH #547).

    Usage: mzt next [OPTIONS]

    Option Default Description

    Result¶

    [{"job_id", "action", "why"}], ordered ESCALATE, UNSTICK, JUDGE, CAST, WAIT, DONE (older submissions first within an action). An empty queue is one DONE row with job_id: null.

    action When
    ESCALATE The score failed or was cancelled, is paused (including paused_at_chain: finished, holding its chain trigger until mzt resume), or has a sheet at a fermata: a person decides
    UNSTICK Running, a sheet is playing, and nothing has been recorded for longer than the idle limit

    mzt verdict¶

    Read a score's review verdict as one word (GH #547).

    Usage: mzt verdict [OPTIONS] JOB_ID

    Finds the newest .md/.txt file in the score's workspace that has a mappable VERDICT: line (the last such line in it) and maps the word: PASS/APPROVE/ACCEPT to PASS, REWORK/REJECT to REWORK, HOLD/BLOCK to BLOCKED. The verdict word is the only interpretation; the extra keys below are read, not judged. A line that lists several verdict words (a prompt template such as VERDICT: PASS | REWORK) is skipped.

    Option Description
    --pattern REGEX Replace the default line pattern; group word (or group 1) is the verdict word
    --workspace DIR Read this directory instead of asking the conductor for the score's workspace
    --accept (--judged) Record the score as judged so mzt next stops saying JUDGE, whatever the verdict
    --json One JSON object, no ANSI 
    {
  "verdict": "REWORK",
  "raw": "VERDICT: REWORK",
  "source_path": "/ws/cycle-state/x-inspection.md",
  "round": 1,
  "findings": ["Email validation accepts a@b with no dot in the domain (validate.py line 41)."],
  "accept": {"ran": 4, "passed": 3},
  "result_path": "/ws/result.md"
}

    verdict is unknown when no file has a mappable line (raw and source_path are then null; the other keys are still filled in). Added in GH #554, so a conductor can brief a rework and quote the checks without reading files:

    • findings: the reviewer's items, verbatim (bullet markers stripped, nothing edited; at most 20 items of 500 characters). Read from the file that carries the verdict, first rule that yields items wins: (1) a section headed FINDINGS (FINDINGS: or ## Findings), its bullets; (2) else the review sheet's own labels, REQUIRED FIXES then FAILURES; (3) else, when the verdict is not PASS, the bullets after the VERDICT: line up to the next heading or UPPER-CASE label (its non-blank lines when it has no bullets). A section ends at the next heading or UPPER-CASE LABEL: line; items such as none or no issues are dropped. A PASS without a FINDINGS section has an empty list.
    • accept: {ran, passed} counted over the validation results the score's sheets recorded in the checkpoint (validation_details per sheet, or its passed/failed name lists). These are the score's validations, the checks mzt status shows as the validation column. {"ran": 0, "passed": 0} means no validation result was recorded or the conductor could not give the state; it does not mean every check passed.
    • result_path: the file named by the task's REPORT field, resolved in the workspace (its basename, as mzt agents run prints it). null when the job has no mzt agents run task file.
    • round: 2 when the task file carries a FINDINGS: line (the rework task), else 1; null when the job has no task file. The task file is the read-only task-* copy mzt agents run leaves beside the bound score in the run dir (found through the job's config_path, which names it as marianne_agent.task.copy, else any task-* file with the six task fields in the workspace).

    mzt agents list and mzt agents run¶

    Cast a persistent agent on a task and start it (SC1c; interim until the one-episode score replaces it). Two commands and a closed vocabulary, so a small model can conduct with mzt wait, mzt verdict and mzt next.

    Usage: mzt agents list [OPTIONS]
Usage: mzt agents run [OPTIONS] NAME

    The agents root is read, never written; run writes only under the runs directory.

    Option Applies to Default Description
    --for TASK.md list Rank by the task's GOAL and FILES words (see below); without it the order is by name
    --free list false Only agents with no running, queued, pending or paused conductor job whose id contains -NAME-
    --task TASK.md run required Six fields: GOAL FILES KIND ACCEPT DO_NOT_TOUCH REPORT; ACCEPT must not be empty
    --class PHASE=CLASS run Repeatable; passed to marianne-agents engage --class
    --inventory FILE run $MZT_AGENTS_INVENTORY Live-verified capability inventory. No default: run is refused with a hint when neither is set. The inventory is not invented
    --runs-dir DIR both $MZT_AGENTS_RUNS_DIR, else ~/Projects/SCORES/agent-runs One directory per run; list reads it for last_outcome
    --agents-dir DIR both $MZT_AGENTS_DIR, else ~/.marianne/agents Agents root
    --json both false One JSON value, no ANSI

    Reservations. A conductor seat that has queued work for a person writes reserved: {NAME: "why, until when"} to ~/.marianne/agents-reserved.yaml (or $MZT_AGENTS_RESERVATIONS). A reserved agent shows free: false, is left out by --free, and run refuses it with AGENT_BUSY naming the reason, so a second seat cannot add a writer or a lifecycle debt to that person. Remove the line to release them. An unreadable file reserves nobody and warns on stderr.

    list prints [{"name", "role", "owns", "free", "open_debt", "last_outcome"}]. An agent is listed when it has profile.yaml and an installed scores/targeted-work.yaml. owns is the profile's owns list (empty when it has none, which is every profile today). open_debt is the pending-lifecycle-debt count that marianne-agents engage refuses on at 3. last_outcome is "PASS 2026-11-12" read from the agent's newest <runs-dir>/NAME-* directory with the mzt verdict finder, or null.

    --for ranking is deterministic: score = |task words & agent words| + 3 for each owned path that is a prefix of a FILES path, highest first, ties by lower open_debt, then by name. Task words are the GOAL and FILES words; agent words are role, group, focus, owns and a fixed role-hint table (builder brings implement, fix, build...). Words are lowercase alphanumerics of three or more characters without a short stoplist; there is no stemming, no synonym handling beyond that table and no model. Limits: it ranks overlap of words, not skill; with empty owns (all current profiles) it is only role and focus words; it never excludes anyone, so combine it with --free.

    run prints {"ok": true, "job_id", "workspace", "result_path"} and exits 0, or {"ok": false, "code", "hint"} and exits 1:

    code Meaning
    TASK_FIELD_MISSING A field is absent or empty, or the task file cannot be read; hint names them
    AGENT_UNKNOWN No such agent with an installed targeted-work score
    AGENT_BUSY The agent has a running, queued, pending or paused job
    DEBT_REFUSED The agent has 3 or more pending lifecycle debts
    SUBMIT_REFUSED No or unreadable inventory, binder refusal (stale evidence, no route), the conductor refused or is down, or the run already exists. Also printed when the conductor accepted the job and it failed immediately inside the early-failure poll — in that case the files are kept and the hint names the job (mzt diagnose JOB). Also printed when the bound score fails to load or fails the score schema (GH #561): the hint starts invalid score FILE: and carries the score's own error, and no job exists, so the files are unbound. A conductor that is alive but not answering is reported as busy in the hint, not as down (it is never one to start)

    list can also print CONDUCTOR_DOWN and COMPILER_MISSING.

    run calls the compiler's engage path in process (bind_engagement: shape targeted-work with --defer-lifecycle, the task copied read-only and injected into every sheet, --class passed through) and then submits through the function mzt run uses, with --escalation on, so a sheet that exhausts its retries stops at a fermata that mzt next reports and mzt resolve answers. Nothing shells out. If the conductor refuses, the bound files are removed so the same task can be run again. If the conductor accepted the job but it failed inside the early-failure poll, the files are kept — the conductor holds a registered job for that score — and the hint names the job with mzt diagnose JOB, so a retry reading already bound has a next step (mzt cancel JOB, then a new task file). The job id is targeted-work-NAME-task-<8 hex of the task file>-<date>; result_path is the REPORT name inside the workspace.

    Interim. targeted-work defers consolidate, reflect, maturity and resurrect: each run adds pending lifecycle debt, which engage refuses at 3. Pay it with a lifecycle-integration engagement.

    mzt doctor¶

    Check Marianne environment health.

    Usage: mzt doctor [OPTIONS]

    Validates that your environment is ready to run Marianne scores. Checks Python version, Marianne installation, conductor status, available instruments, and safety configuration. This command works without a running conductor — it is designed to be the first thing you run after installation.

    Options¶

    Option Short Default Description
    --json false Output results as JSON
    --clean false Delete storage-hygiene findings after explicit confirmation
    --live false Also run instruments check --live on every ready agent instrument. A failed probe becomes a warning naming the mode and classification; no instrument passing is an error. Spends model calls; use it after installing or upgrading a CLI, or before a long run

    Checks Performed¶

    Check What It Verifies
    Python Version 3.11+ installed
    Marianne Marianne package installed, version displayed
    Conductor Whether the conductor daemon is running (PID file + process check)
    Instruments Configured instruments, binary readiness, execution readiness, and runtime rate-limit state when the conductor is running
    Safety Whether cost limits are configured
    Storage Cleanable stale state or backup artifacts
    Instrument hygiene User- and venue-layer profiles that no score the conductor has been given names and no class chain includes (GH #443). Reported only, never deleted: a seat is an alias over an existing profile, so a profile nothing names is archived by a person or kept by submitting the score that needs it. --json lists them under unreferenced_profiles. Skipped before the conductor has ever run. Reads the registry of the conductor the CLI addresses (--conductor-clone selects the clone's)
    Providers For each mcp_pool.servers entry whose command runs REA (Reverse Engineer Anything, the rea-agents package), runs REA's own read-only rea doctor --json with the entry's interpreter and script and reports its verdict and each failing check in REA's words (a Ghidra release it does not accept, a Java probe past its deadline). A gap is a warning; nothing is installed or repaired. --json lists them under provider_checks (GH #499)
    Musician hooks The hooks block of the user-level Claude Code settings (~/.claude/settings.json), by event and the hook command's program name only (never arguments, env or inline scripts: <inline script>, <unrecognised>). SessionStart/UserPromptSubmit hooks are flagged as adding to every sheet's context unless they check MARIANNE_SHEET; PreToolUse/PostToolUse/Stop hooks as running in musicians (intended for safety hooks). A warning when a profile sets cli.command.disable_hooks_args (all hooks off) while PreToolUse/PostToolUse hooks exist, since musicians run auto-approved. --json: musician_hooks (GH #536)
    Credential exposure Ready agent profiles using the explicit cli.command.inherit_env opt-out while credential-shaped variables are set (GH #335). Profiles are named without printing values; declare required_env or remove the opt-out to clear the warning
    Credentials no longer reaching a profile A ready personal/venue profile with no required_env, running an executable a shipped profile authenticates by environment (claude, codex, gemini, agy, goose), while those variables are set in this environment: since GH #335 they are filtered by default, so the instrument authenticates differently from the shell it was tested in. Declare required_env with the variables it reads, or required_env: [] if it uses its own store
    Gemini auth inference A ready gemini-executable CLI profile with none of GEMINI_API_KEY (primary, GH #469), GOOGLE_API_KEY, GOOGLE_APPLICATION_CREDENTIALS, GOOGLE_CLOUD_PROJECT, CLOUDSDK_CONFIG set is reported unsupported with a message naming the variables, instead of ready: the default individual-tier OAuth path cannot run a headless prompt. An auth signal is a readiness hint, not proof — verify with mzt instruments check <profile> --live (see the instrument guide's Gemini section)

    Every command that answers "can this instrument run here" — doctor, instruments list, instruments check, instruments classes check and classes write — uses one probe with four states (GH #447):

    Probe state Meaning Shown as
    ready Can run now: CLI binary on PATH, or a local (loopback) server that answers and serves the profile's default_model, or a native instrument ✓ (doctor ok; list ✓ ready)
    unavailable Cannot run: binary missing, profile declared unsupported, no command, or the local server answers but does not serve the model (the served models are named) · (doctor optional; list ✗ not found)
    unreachable A local server that does not answer · (doctor optional; list ✗ not answering)
    unchecked A remote HTTP endpoint; never probed because it needs credentials ? (doctor and list unchecked)

    "Marianne is ready" means at least one agent instrument is ready (the raw shell cli profile does not count). With none, doctor reports an error naming what to install or pull. Runtime rate-limit state is shown when the conductor is running.

    mzt recover¶

    Recover sheets that completed work but were incorrectly marked as failed.

    Usage: mzt recover [OPTIONS] JOB_ID

    Runs validations for failed and cascade-skipped sheets without re-executing them, in the same context execution validates in (the sheet's stage, instance, movement, prompt variables and open loop indices), so a condition: "stage == N" rule applies to exactly the sheets it applies to in a run.     --dry-run -n false Check validations without modifying state

mzt recover my-job

    mzt instruments prices¶

    Compare every profile's model prices with models.dev; --write updates the builtins.

    Usage: mzt instruments prices [OPTIONS]

    Marianne prices a sheet from the models rows of the profile it ran on. Those rows are maintained by hand and drift as providers reprice. This command fetches models.dev api.json (MIT, bot-synced; input, output, cache-read and cache-write prices per model), maps each profile's model ids to a provider (claude-code → anthropic, its glm-* rows → zai-coding-plan; codex-cli → openai; gemini-cli → google; opencode zai-coding-plan/* → zai-coding-plan, the rest → openrouter) and reports each row as one of:

    • match: every price models.dev carries equals the row's. An unset cache price is compared at the rate the estimate would charge (the input rate).
    • drift: at least one price differs. The table shows the field, ours, and theirs in USD per 1K tokens.
    • absent: the provider is mapped but models.dev has no such model id (a retired id, a :free route).
    • unmapped: a profile with no provider mapping: a subscription route priced at $0 on purpose (antigravity), a local server, or a harness whose ids are its own.

    Builtin and user layers are compared separately, so a user claude-code.yaml does not hide drift in the builtin. Nothing refreshes at run time: prices change in a commit, after a person reads the table.

    Options¶

    Option Short Default Description
    --json false Output as JSON (counts, rows, written, refused, source)
    --write false Rewrite the drifted price fields on the BUILTIN profile files in place, keeping their comments. User (~/.marianne/instruments/) and venue (.marianne/instruments/) files are reported under refused and left alone: they are yours to edit
    --offline false Do not fetch; compare against the last saved snapshot
    --snapshot PATH ~/.marianne/cache/models.dev.api.json Compare against this api.json instead of fetching. Every successful fetch saves the default path
    --all false Also list rows that match, are absent, or are unmapped

    Exit codes: 0 nothing drifts (or every drifted row was written); 1 a drifted row remains; 2 the snapshot could not be fetched or read.

    Examples¶

    # Report drift
mzt instruments prices

# Update the builtin rows in a source checkout, then review and commit the diff
mzt instruments prices --write && git diff src/marianne/instruments/builtins/

# CI or an air-gapped host: compare against a pinned snapshot
mzt instruments prices --snapshot ./models.dev.api.json --json

    Code Meaning
    0 Conductor started, or a conductor was already serving (its PID is printed). A process supervisor must treat the second case as success: with Restart=on-failure an exit 1 here restarted mzt start every 30 s against a hand-started conductor (GH #459).
    1 Configuration error, the conductor failed to start, or a draining conductor did not exit within the 30s supersede budget

    mzt stop¶

    Stop the running conductor. Non-blocking by default: after the safety check (and any confirmation) the signal is sent and the command returns without waiting for the conductor to exit. If scores are actively running, warns and asks for confirmation before proceeding. Stopping the conductor while scores run can orphan active agents and corrupt score state.

    Usage: mzt stop [OPTIONS]
    Option Short Default Description
    --pid-file ~/.config/mzt/mzt.pid Path to PID file
    --force false Skip safety check, send SIGKILL instead of SIGTERM
    --wait Wait for the conductor to exit after signaling. --wait= (equals sign, empty value) waits with the default 30s budget; --wait=SECONDS (or --wait SECONDS) sets a custom budget. Budgets must be finite and non-negative; --wait=0 keeps the signal-and-return behavior.
    --conductor-clone Stop a clone conductor; use --conductor-clone= for the default clone or --conductor-clone=NAME for a named clone

    Safety guard: When scores are running, mzt stop probes the conductor via IPC to check for active scores. If any are found, it warns with the count and asks for confirmation. The --force flag bypasses this check entirely and sends SIGKILL.

    After signalling, the command lists the in-flight sheets the graceful drain will wait on (<job> sheet <n> on <instrument>/<model> for <elapsed>s); a boundary-paused job's current sheet is among them until it ends. With a positive --wait budget, the command blocks until the conductor exits (prints Marianne conductor stopped) or exits 1 with did not exit within <budget>s. It is still draining. followed by the sheets a fresh probe says it is still waiting on. A graceful drain can take up to shutdown_timeout_seconds (default 300s) plus teardown while running jobs checkpoint — a --wait budget shorter than that is a bounded poll, not a guarantee.

    # Normal stop (warns if jobs running; signals and returns immediately)
mzt stop

# Force stop (SIGKILL, no safety check)
mzt stop --force

# Block up to the default 30s for the conductor to exit
mzt stop --wait=

# Block up to 60s
mzt stop --wait=60

    --output required Destination JSONL file (private local export)

    Directories are read as trusted local input: YAML is preserved byte-for-byte (comments and line endings included), nested repositories (including rosetta-corpus), symlinks, and .lock files are excluded. Telemetry JSONL is not trusted: every accepted score passes through the telemetry sanitizer again, and malformed or unsupported envelopes are skipped and counted in a warning without logging their contents. Deduplication hashes exact output text (no YAML normalization); when exact duplicates occur across sources, the repository example wins, including its rationale.

    The destination is written atomically (temp file + rename, fsync'd) and must differ from the sources, the consent state file, and reserved .lock names, and must not replace a source score. Review the output before sharing it — the corpus tooling is local-only and asserts no redistribution or training rights.

    mzt corpus build --sources examples,scores --output /tmp/composition-corpus.jsonl

    mzt corpus stats¶

    Count distinct outputs and annotations against the 200-example volume target.

    Usage: mzt corpus stats [OPTIONS]
    Option Short Default Description
    --sources examples,scores Comma-separated score dirs or telemetry JSONL spools
    --json false Emit machine-readable counts

    Reports total_examples (after deduplication), by_source_kind, by_category, annotated (records carrying a human rationale), and meets_target against target_volume (200). Volume alone does not establish diversity, permission, or training readiness.

    mzt corpus stats

    Error Codes¶

    Marianne classifies every execution failure into a structured error code. Use mzt errors <job> --code E001 to filter by code. The error code determines retry behavior, delay timing, and severity.

    E0xx — Execution Errors (process-level failures)

    Code Name Retriable Severity Delay
    E001 EXECUTION_TIMEOUT Yes ERROR 60s
    E002 EXECUTION_KILLED Yes ERROR 30s
    E003 EXECUTION_CRASHED No CRITICAL —
    E004 EXECUTION_INTERRUPTED No ERROR —
    E005 EXECUTION_OOM No CRITICAL —
    E006 EXECUTION_STALE Yes WARNING 120s
    E009 EXECUTION_UNKNOWN Yes ERROR 10s

    E006 (stale detection) fires when an agent produces no output for longer than stale_detection.idle_timeout_seconds. It is distinct from E001 (backend timeout) — stale detection kills agents that go silent, while backend timeout caps total execution time.

    Musician messaging¶

    Inside a running job, shell-capable instruments can exchange notes through the scratch-owned mailbox, independent of harness adapters:

    mzt mail send 2 "The shared interface is ready"
mzt mail send all "Review the updated interface before editing"
mzt mail read
mzt mail read --since 123

    send accepts a concrete sheet number or all (all initialized inboxes except your own). read prints JSONL records with id, timestamp, sender, recipient, and body. IDs are opaque, increasing cursors local to your inbox; pass the last received ID to --since to exclude messages already seen. The backends export MARIANNE_MAILBOX and MARIANNE_SHEET; the CLI can also resolve the inbox root from MARIANNE_SCRATCH/mailbox. It refuses to guess a job or sheet when that context is missing. Messages are data, not instructions. Send events record identities and UTF-8 byte counts without message bodies. Inbox contents follow the job's scratch cleanup policy; a job that ends in an error, timeout, or cancellation keeps its scratch (and with it the inboxes) for post-mortem.

    mzt diagnose JOB includes mailbox traffic (sender, recipient, UTF-8 byte count, per-inbox counts, and first/last timestamps); --json adds mailbox_traffic when messages exist. The conductor records each send and its summary when the job settles at any terminal status — COMPLETED, FAILED, or CANCELLED — so a job that died mid-fan-out still logs every delivered send, and retains this metadata in the job checkpoint before scratch cleanup. Message bodies are excluded from traffic logs and diagnosis.

    Debugging Protocol¶

    When a job fails, follow this order:

    # 1. Check current status (routes through conductor)
mzt status my-job

# 2. Get full diagnostic report
mzt diagnose my-job

# 3. View error history
mzt errors my-job --verbose

# 4. Check logs
mzt logs my-job --level ERROR

# 5. Try recovery (re-validate without re-execute)
mzt recover my-job --dry-run

    mzt remediate¶

    Diagnose failed sheets using the same remedy registry and healing coordinator as conductor self-healing. The command reads persisted job context and attempt history from the authoritative registry; it does not update checkpoint status or restart execution.

    mzt remediate JOB_ID --dry-run
mzt remediate JOB_ID --sheet 2 --yes
mzt remediate JOB_ID --json
    Argument / option Purpose
    JOB_ID Registered job identifier
    --workspace, -w Override the workspace used for remedies and spec loading
    --sheet INT Select a single sheet, including a nonterminal sheet with an error
    --yes Approve suggested remedies without prompting
    --dry-run Preview remedies without applying them or prompting
    --json Emit reports as JSON on stdout; confirmation prompts go to stderr

    AUTOMATIC remedies apply unless --dry-run is set. SUGGESTED remedies ask for confirmation unless --yes is set. DIAGNOSTIC remedies provide manual guidance. Spec fixes and re-compose are guidance-only proposals in this version: the command does not edit specifications or execute re-compose. Config loading and spec corpus warnings appear in the report. Applying offline remedies requires a terminal job; use --dry-run to inspect other jobs. Without a workspace override, the stored configuration supplies the workspace.

    Use mzt diagnose for read-only job reporting and mzt recover for validation-based recovery. Remediation repairs supported causes or explains the next manual action; it does not mark a failed sheet complete.
